Playbook

Opening, updating, and closing branches

GitAgent turns real git branches into scoped memory for a project. This walks through starting a project, when to open a branch versus nest one, and exactly what each operation changes in STATE_TRACKER.md and a branch's own MEMORY.md — including a step-by-step look at the files themselves.

01

Start a project

Before any branch exists, a project needs a STATE_TRACKER.md — the persistent, always-current record of what's going on. gitagent init builds it from a few questions.

$ python -m gitagent.cli init
Project name: Search Service
What are you building? A /search endpoint backed by an embeddings index
Why does this matter to you? (optional) Want a record of why I made each call, not just what I built
How do you want to work on it? (optional) Small steps, one branch per concern

Each non-blank answer is polished into a clean sentence by a single local-Ollama call — your words, tidied up, nothing invented — and written into STATE_TRACKER.md's Overview & Mission section. If the directory isn't a git repo yet, init creates one on main; if it already is one, it just requires that repo to already be on main. It also creates an empty branches/ directory and makes the first commit. Run it once, at the very start — it refuses to touch a project that already has a STATE_TRACKER.md.

02

The branch lifecycle

Every piece of work becomes a real git branch with its own MEMORY.md. Three operations carry it through: open it, log notes as you go, close it when it's done.

Start

open_branch

Use it when you're about to start a distinct piece of work — a feature, a fix, a question worth its own scoped memory. Give it a name and a one-line goal.

No Ollama call
As you go

update_branch

Use it every time you make a decision or finish a step worth remembering — as often as you like. It's just a timestamped note, cheap enough to call constantly.

No Ollama call
Finish

close_branch

Use it once the work is actually done — merged, resolved, abandoned-but-documented. It's the one step you can't easily undo, so don't call it mid-work.

02.1

Top-level, or nested?

open_branch takes a base — which branch it's opened from. Left as the default, main, it's a normal top-level branch. Pass another open branch's name instead, and it nests under that branch rather than under main.

Rule of thumb: open top-level when the work is its own concern someone would look for in STATE_TRACKER.md. Nest it when the work only makes sense in service of something already open — a sub-question, a follow-up detail, a fix scoped to one in-progress feature.

04

Quick reference

The same four commands, side by side.

Command When STATE_TRACKER.md MEMORY.md
gitagent init Once, at the very start of a project. Creates it. —
open-branch name desc [-b base] Starting a distinct piece of work (or nesting one under work already open). +1 Active row — only if base is main. Creates branches/name/MEMORY.md. If nested, also adds an Active line to the root's Sub-Branches.
update-branch name note Any time you make a decision or finish a step worth remembering. As often as you like. Untouched. Appends a timestamped bullet to that branch's own Decisions Log.
close-branch name Once, when the work is actually finished. Row flips to Completed + Ollama summary — only if the branch was top-level. Merges and archives it (branches/archived/…, never deleted). If nested, flips its line under the root's Sub-Branches to Completed + summary instead.
graph [-o out] Any time you want to see the branch/commit structure. Read-only. Read-only.
05

Things worth knowing

Do I need Ollama running for all of this?
Only for close_branch (and the polish step in init). Opening and updating branches never call it — they're plain structured logging.
I checked out a branch that isn't main and STATE_TRACKER.md looks out of date. Is that a bug?
No — it's only guaranteed current on main. Any other branch's copy is a snapshot from whenever it forked. Use git show main:STATE_TRACKER.md to see the real, current table from anywhere.
Does closing a branch delete anything?
No. A closed branch's MEMORY.md moves to branches/archived/… — the raw log stays retrievable forever, it's just no longer the active copy.
How deep can nesting go?
As deep as you want. A grandchild branch still logs into the same root's Sub-Branches section as a direct child would — it's flattened, not indented, so STATE_TRACKER.md never grows past one row per top-level branch no matter how much nested work happens underneath it.
What if I close a nested branch before I'm done with its parent?
That's the normal order, not an edge case — close the nested branch first, its summary lands on the parent's Sub-Branches, then close the parent whenever that's actually finished.
